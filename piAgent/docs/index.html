PI Agent

PI Agent packages the PI coding agent as a manual-start Ploinky worker. It runs asynchronous coding tasks in a task-specific Bubblewrap namespace, streams provider output, and preserves PI sessions for follow-up turns.

Use PI Agent

Start PI directly through Ploinky when you want its native interactive CLI:

ploinky cli piAgent

For an AchillesCLI-owned background task, request PI by name or execute its launcher:

Ask PI to investigate the failing integration test.
/exec launch-pi Investigate the failing integration test.

The worker runs independently after submission. Use AchillesCLI's /tasks, /task view, /task continue, and /task stop commands to manage the task.

Task lifecycle

Execution behavior

PI runs in JSON event-stream mode with an explicit provider session identifier and session directory. The wrapper forwards assistant text and textual tool output as they arrive, removes duplicate cumulative tool updates, and uses the final assistant message as the task result. Thinking records, signatures, encrypted content, and usage metadata remain outside the visible task log.

The worker stores the provider session and original project directory behind an opaque continuation handle. A follow-up turn loads that private record and resumes the same PI session. AchillesCLI keeps its original local task identifier even though Ploinky creates a new remote task for the continued turn.

Models and provider state

Initial delegated work uses PI's provider-owned model selection unless an authorized task caller supplies an override. Before continuation, PI combines its persistent global settings with project-local PI settings and applies valid provider, model, and thinking-level choices. Missing or malformed settings fall back to PI's native session-resume behavior.

Generated-local mode can route PI through its repository-owned Soul Gateway extension and a scoped loopback broker. Ordinary provider authentication remains in PI's persistent home and can be managed through the typed task-session control flow.

Security and boundaries

Every initial and continued provider process runs inside a nested Bubblewrap namespace. The canonical project directory is the only writable project bind; sibling projects and the broader workspace are not mounted. Provider configuration and session directories receive only the access required for PI to operate. The task environment excludes raw Ploinky credentials and provider secrets, while networking remains available for provider calls.

The worker fails closed when it cannot establish the task sandbox. Its readiness check proves that the selected sandbox mode can start PI before Ploinky marks the agent ready. The shared continuation, authentication, and sandbox requirements are defined in DS010 ecosystem integration.
