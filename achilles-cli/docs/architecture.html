AchillesCLI Architecture

AchillesCLI is a local agent runtime built around one fixed workspace, a trusted authorization boundary, and a sandboxed execution environment. Its architecture stays fundamentally the same whether the user starts it directly or reaches it through Ploinky; Ploinky adds lifecycle management, authenticated routing, WebChat transport, and access to other agents around the same core runtime.

System at a glance

The architecture separates the component that decides whether a Bash command may run from the component that executes it. The trusted side establishes the session boundary and handles approval decisions. The sandboxed side interprets requests, chooses skills, calls language models, and runs approved commands. This separation prevents the agent from granting itself broader permission while it is working.

Core components

Session controller

The session controller converts a launch request into one running AchillesCLI session. It resolves the selected working directory, fixes that directory as the workspace boundary, loads the requested runtime settings, and chooses the interaction mode. A prompt supplied at startup produces a single result and then ends the process. An interactive terminal starts a REPL. A Ploinky WebChat launch selects the structured message loop used by the browser interface. Once the session starts, the agent cannot silently replace the workspace with a broader directory.

Trusted authorization broker

AchillesBroker is the small trusted process outside the sandbox. It owns the permission mode, receives authorization requests for Bash, presents approval choices to the active user interface, and controls the lifetime of the sandboxed agent process. The broker never runs the requested Bash command itself. It only decides whether the sandboxed executor may run that exact request, which keeps execution and authorization under different authorities.

In ask-for-approval mode, the broker can allow one call, deny it, or approve that exact call for reuse during the session. A denial becomes a normal tool result so the agent can continue planning without pretending that the command ran. In full-access mode, Bash no longer pauses for approval, but every command remains inside the same workspace sandbox; the name refers to automatic execution within the workspace, not unrestricted access to the host.

Workspace sandbox and Bash executor

Bubblewrap creates the filesystem view used by the agent and every Bash child process it starts. The selected workspace is writable, required runtime resources are mounted with limited access, and unrelated host paths are absent. When Ploinky selects a directory nested below its workspace root, the broker validates and separately mounts only the outer .data/achilles-cli private-state directory as writable; it does not expose the rest of the outer workspace. Settings, history, repositories, sessions, tasks, and AKU storage reject symbolic links at their owned storage children before access or removal. The Bash executor lives inside this environment, starts approved commands there, captures their output, and returns that output to the agent as a tool result. A failed or blocked command is never retried outside the sandbox.

This is a filesystem confinement boundary, not a separate network security boundary. Network access follows the surrounding runtime, while filesystem visibility remains restricted to what the session explicitly exposes.

Agent runtime

AchillesAgentLib MainAgent is the reasoning and tool-execution core inside the sandbox. It receives the user's request and the conversation state, discovers the skills available to the session, decides which skill or tool should act, and returns the resulting answer. Natural-language requests may require several planning and execution steps. Slash commands bypass that open-ended planning when the user has already named the exact operation.

The runtime also coordinates cancellation, refreshes the skill catalog after relevant changes, and keeps the interaction interface separate from skill execution. Terminal and WebChat users therefore reach the same underlying agent behavior even though their messages and progress updates use different transports.

Command and skill layer

A skill packages one reusable operation together with the instructions and optional executable behavior needed to perform it. The skill layer discovers built-in and workspace-provided skills, validates their descriptors, exposes direct slash commands, and makes enabled skills available to MainAgent. Deterministic commands such as reading, validating, or testing a named skill route directly to the corresponding behavior; broader requests let MainAgent coordinate multiple skills.

Skill enablement belongs to the workspace, while extra skill roots supplied at launch belong only to that process. Ploinky can contribute additional managed repository roots, but their skills enter the same catalog and follow the same enablement and sandbox rules as locally discovered skills.

Language-model boundary

All language-model calls pass through AchillesAgentLib LLMAgent. AchillesCLI selects a tier or an explicit model and supplies the conversation context, but it does not call individual model vendors directly. The Soul Gateway validates the requested model and applies the configured provider routing. Runtime configuration may come from environment-derived defaults or explicit host overrides, while the selected workspace may persist the user's model choice.

Workspace state

AchillesCLI keeps durable state with the workspace so that a later process can resume the same user context. This state includes conversation sessions, selected runtime preferences, skill enablement, and journals for background work. Process-only state, such as a reusable approval for one exact Bash call, disappears when the running agent ends. Keeping these two lifetimes separate prevents a temporary authorization decision from becoming a permanent workspace permission.

Independent execution

When AchillesCLI runs independently, the user starts the local executable from the directory in which the agent should work. The local process owns the complete session lifecycle: it selects the workspace, starts the broker and sandbox, reads terminal input, displays approvals, and prints the final response. The user may run one prompt or remain in the interactive terminal. The development runtime must expose its selected AchillesAgentLib checkout through the standard package link; AchillesCLI never installs or clones a competing copy. Operating-system prerequisites are installed separately, and model-routing credentials and endpoints are supplied by the local environment.

Independent mode does not require a Ploinky workspace, Router, AgentServer, or browser interface. It provides the local agent, its skills, its workspace state, and the same Bash confinement directly in the terminal. Features that depend on Ploinky services—such as the dedicated WebChat transport, managed agent discovery, or delegation to another registered agent—are not supplied by the standalone process itself.

Execution through Ploinky

Ploinky surrounds AchillesCLI with a managed runtime. It installs and starts the agent, chooses the mounted workspace, provides an authenticated identity, makes the local Soul Gateway available, and connects AchillesCLI to Ploinky's routing and service lifecycle. AchillesCLI still creates its own broker and Bubblewrap boundary inside that managed environment. Ploinky does not grant Bash permission on behalf of the user and does not replace MainAgent's skill execution.

The user can enter the same CLI through Ploinky's terminal command or use the dedicated WebChat interface. In WebChat mode, ordinary terminal text is replaced by structured messages. User prompts arrive as message envelopes, and AchillesCLI publishes answer, progress, approval, session, skill-state, workspace-file, and background-task events that the browser can render. Approval remains attached to the original pending Bash request, so a browser decision resolves the same authorization flow used by the terminal.

Ploinky also makes optional delegation possible. Launcher skills can ask a registered AgentServer to start work in another agent and return immediately with a background task. AchillesCLI remains the user-facing owner of the task journal, status, cancellation, and continuation handle, while the target agent owns its provider-specific process and session. WebChat displays this state but does not become its persistence owner.

Invariants shared by both modes

The selected workspace remains the only automatically writable filesystem tree. AchillesBroker remains outside the sandbox and never executes Bash. MainAgent and Bash children remain inside the sandbox. Every language-model request goes through LLMAgent. Permission choices change whether a command needs confirmation, not which host files it can reach. Durable user state remains associated with the workspace, while temporary execution authority remains associated with the running process.
