## Introduction

Promotion Scout lets an operator describe interests in the web interface of the `promotionScout` Ploinky agent, choose the sites to watch, start periodic collection on demand and review new public discussions with original passages, including everything collected before ranking. Scout never writes or posts replies.

## Core Content

### Main Behavior Components

| Name | Explanation |
| --- | --- |
| Ploinky agent and service lifetime | The install step prepares data, model and RSSHub before every start; AgentServer serves the MCP tools and the interface through the router, and the agent daemon keeps RSSHub running and starts cycles; nothing is collected until asked. |
| Topics with search terms and tags | The operator describes each interest and gives the short search terms and tags that sites understand; the agent keeps them in its SQLite database. |
| Watched site catalog | Built-in and operator-added sites turn topics into RSS/Atom feeds; the operator can enable, disable, add and delete sites in the Sites tab. |
| Operator-started monitoring | Start runs one cycle as a task within seconds and repeats it at the chosen interval, from hourly to weekly, across agent restarts; Stop ends cycles without stopping RSSHub. |
| Polite feed collection | Each run polls due feeds hourly at most, spaces requests per host and pauses a host that refuses. |
| Local ranking with visible collection and new results | The operator sees every collected entry with its score and every passing result, and new results stay marked until seen. |
| Discussions and subtopics | For results of topics with subtopics, Scout reads the post and its first 10 comments and shows which subtopic, if any, the discussion is about. |

### Ploinky agent and service lifetime

The operator uses Scout as the [Ploinky agent](../wiki.html#definition-ploinky-agent) `agent:AchillesCLI/promotionScout` and opens `/promotionScout/` on the Ploinky router, which admits only signed-in workspace users and redirects to the [web interface](../wiki.html#definition-web-interface) at `/promotionScout/web/`. Before every start, Ploinky runs the agent's [install step](../wiki.html#definition-install-step), `sh /code/scripts/install.sh`: it requires the npm packages Ploinky prepared from `package.json` (`SETUP_REQUIRED` names missing ones), then under the lifecycle lock creates `config.json` and SQLite in the [data directory](../wiki.html#definition-data-directory) `.data/promotionScout`, downloads the default model when it cannot be loaded locally and builds the pinned RSSHub. Completed stages are skipped, so only the first start downloads and builds; a failed stage stops the start with `SETUP_INCOMPLETE` and is retried at the next start.

`scripts/startAgent.sh` then starts the bundled Ploinky AgentServer, which runs one process per [MCP tool](../wiki.html#definition-mcp-tool) call and queues [cycle tasks](../wiki.html#definition-cycle-task), and the [agent daemon](../wiki.html#definition-agent-daemon), and stops the container when either exits. The daemon takes the lifecycle lock, marks runs left `running` as `interrupted`, synchronizes the built-in site catalog, starts or reuses RSSHub at `http://127.0.0.1:1200` inside the container, checks it every 30 seconds and restarts it when it stopped, and writes a heartbeat that the Monitor tab shows. Starting the agent must not collect anything unless monitoring was left on. When the agent stops, the daemon stops only the RSSHub process whose recorded Linux identity proves it started it. The lifecycle specification defines installation and ownership and the agent runtime specification defines tools and tasks.

### Topics with search terms and tags

The operator adds a [topic](../wiki.html#definition-topic) in the Topics tab, usually a few words such as `AI gaming news`; the model compares entries with it and it identifies the topic. Up to five [search terms](../wiki.html#definition-search-terms) are short phrases sent to search sites, and up to five [tags](../wiki.html#definition-tags) are subjects sent to tag sites. Both are optional: when left empty, Scout derives them from the topic's significant words, shows the derived values in the form while the operator types and marks them `auto` in the topic table. Stored values always replace derived ones. Equivalent spacing and capitalization must not duplicate a topic, a term or a tag. Edit opens one dialog for the topic text, terms, tags and subtopics, and clearing a list returns it to derivation. Changing the text renames the topic in place: its subtopics, history and fields stay, while earlier scores no longer match the new intent, so its results reappear once the next run re-ranks them. A text already used by another topic, active or removed, is refused. Removing a topic deactivates it and hides its results while keeping its history; adding it again restores that history. Changes take effect at the next run.

### Watched site catalog

The Sites tab lists every [site](../wiki.html#definition-site) with its kind, address template, number of feeds it currently produces, entries collected and status. A `search` site inserts search terms, a `tag` site inserts normalized tags and a `feed` site is read once for all topics. Scout ships seventeen built-in sites from `config/sites.json`: Reddit, Hacker News and Bluesky search; Mastodon, DEV Community, Medium, Lobsters, Stack Overflow and Lemmy communities tags; Product Hunt, Slashdot, Hugging Face daily papers, Lemmy, Ask HN, MetaFilter, Ask MetaFilter and Tildes as general feeds. The operator can disable any site, add sites with a feed URL, a web page advertising a feed, a template with `{query}` or `{tag}`, or an RSSHub route, and delete sites they added. Scout does not search the open web; discussions on sites outside the catalog are not found. The provider specification defines templates, the catalog and collection limits.

### Operator-started monitoring

In the Monitor tab the operator chooses an interval, every 1, 2, 4, 6, 8 or 12 hours, once a day, every two days or once a week, and presses Start monitoring, which calls `scout_monitor_start`. The tool saves the interval and the monitoring flag in SQLite and returns; the agent daemon reads the flag within two seconds and starts the first cycle by calling the internal tool `scout_run_cycle` through the router. Scout must start the next cycle no earlier than the chosen interval after the previous cycle started, or as soon as the previous cycle ends when it took longer. A feed returns only its newest entries, typically 20 to 50, so with a daily or longer interval a busy site or search term can publish more posts between runs than its feed still lists, and those posts are missed; hourly or few-hour intervals suit busy sources. The button becomes Stop, and the interval cannot change while monitoring runs. Stop calls `scout_monitor_stop`, which clears the flag; the running cycle task notices it within two seconds and aborts between requests and ranked items, keeping everything already committed, and the daemon starts nothing further, cancelling the task if it is still running a minute later. Stop never stops RSSHub.

Every cycle is recorded as a [run](../wiki.html#definition-run) with its start and end time, status (`ok`, `partial`, `failed`, `aborted` or `interrupted`), counts and error messages, and runs as one cycle task whose standard-error lines form the live cycle log in the Monitor tab. A run whose task ended without finishing it, for example because the agent restarted, becomes `interrupted`. The monitoring flag and interval are saved in SQLite, so monitoring resumes after an agent restart until the operator presses Stop; a saved interval that is no longer offered falls back to hourly. The one-hour minimum matches the hourly feed cooldown so each cycle can poll every due feed.

### Polite feed collection

Each run builds the feed list from active topics and enabled sites, then polls every feed whose last attempt is at least one hour old. Feeds shared by several topics are polled once. Requests to one host are spaced by at least one second, ten seconds for Reddit, and a 429 is never retried. A host that answers 403 or 429 is paused for six hours and its other feeds wait without losing their turn. Unknown tags are explicit skips. SQLite preserves entries, validators, errors and pauses so later runs reuse earlier work while new entries keep arriving. Failed feeds make the run `partial` and appear in its errors.

### Local ranking with visible collection and new results

After collection, each run ranks English feed entries from the last seven days with the default EmbeddingGemma model on CPU in a worker thread of the cycle task; a local detector keeps non-English entries out of ranking. Only entries with verified [feed provenance](../wiki.html#definition-feed) are ranked. The model compares the topic description with the entry title and feed text; for sites whose feeds carry only a title, the title is what is compared. The model loads at the start of a run and is released at its end. Cached vectors and scores remain isolated by model semantics, intent and content. An inference failure fails the run without substitute scores.

The Collected tab (step 2) shows every feed entry stored for active topics before the threshold, with its similarity score, `passed`, `below threshold`, `not evaluated` or `not English` status, and a new mark when the latest run first collected it. The Feeds tab (step 1) shows each concrete feed with its site, topic and outcome. The Topic matches tab (step 3) shows every URL whose score reached the model's threshold (0.25 for EmbeddingGemma) for an active topic, deduplicated across topics, with the site that delivered it, its matching topics and original passage; results and collected entries can be filtered by site, and results sorted by novelty, time found or score. A result is new from the run that first found its URL until the operator opens its link or marks it reviewed, and a URL is never marked new twice. The operator decides whether to post outside Scout.

### Discussions and subtopics

The operator adds [subtopics](../wiki.html#definition-subtopic), free texts describing a specific angle, to a topic in the Topics tab. After each run ranks entries, Scout reads the [discussion](../wiki.html#definition-discussion) behind every result of a topic with subtopics that it has not read yet: every due discussion in each run, in batches that alternate between topics, through public discussion APIs or feeds where sites offer them and through page text otherwise, with the same per-host spacing and refusal pauses as feeds. Each result belongs to its best topic, the matching topic with the highest score, and its discussion is read only when that topic has subtopics. Scout compares the title, post and first 10 comments only with the best topic's subtopics, using the same local model, and never judges the topic again. A subtopic matches when its score reaches the subtopic threshold, 0.35 for EmbeddingGemma, and the best matching subtopic wins. The Subtopic matches tab (step 4) lists matched discussions first, new ones first among them, with every subtopic's score and the post and comments; discussions that matched nothing or could not be read stay visible on request. The expandable section also lists the [generated comments](../wiki.html#definition-generated-comment) that earlier versions wrote for the discussion, read-only. Scout never writes or posts replies. The discussions specification defines sources, limits and scoring.
