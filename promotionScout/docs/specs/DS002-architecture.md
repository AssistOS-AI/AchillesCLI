## Introduction

One [data directory](../wiki.html#definition-data-directory) per agent lets the daemon, every tool call and every cycle task share interests, content, runs, monitoring state and previous results.

## Core Content

### Data ownership

Inside the agent the data directory must be the volume `.data/promotionScout`, mounted at `/data` and named by `SCOUT_DATA_DIR`; `/code` is read-only and must never receive data. When `SCOUT_DATA_DIR` is not an absolute path, the code falls back to `~/.local/share/promotion-scout/`, with an absolute `XDG_DATA_HOME` replacing the base, which serves tests and development. Storage must not depend on the working directory. `config.json`, `models/`, `services/` and `runtime/` accompany `scout.sqlite`. SQLite WAL and shared-memory files are sidecars of the same database. Backups must use SQLite-aware tooling or preserve all live database files with the agent stopped.

| Table | Responsibility |
| --- | --- |
| topics | Normalized description/key, active flag, search terms and tags. |
| projects | Internal intent and ranking hash referenced by topics; not a public project concept. |
| sites | Built-in and operator-added sites: kind, address template, options, built-in flag and enabled flag. |
| sources / project_sources | Concrete feed identity, the site that produced it, polling state and topic associations; `enabled` marks the feeds the current terms, tags and sites produce. |
| source_attempts | Hourly cooldown timestamps, including failed and interrupted attempts. |
| items / source_items | Normalized content, detected language and source associations; `fetched_at` is the first collection time. |
| feed_source_items | Source/item/content-hash provenance certifying collected feed entries. |
| embeddings | Float32 vectors keyed by model namespace, role and text hash. |
| evaluations | Scores and passages keyed by intent, item content and model semantics. |
| runs | One row per monitoring cycle: start and end time, status, counts and error messages. |
| findings | First appearance of each passing URL: item, run, time found and time seen. |
| settings | Values kept between agent starts: the monitoring interval (`intervalHours`), the monitoring state (`monitor:running`, `monitor:lastStartedAt`, `monitor:taskId`, `monitor:lastTaskId`), the daemon heartbeat (`monitor:daemon`) and per-host pauses after 403 or 429 responses. Rows written by earlier versions, such as comment instructions, are ignored. |
| subtopics | Free-text subtopics of a topic, unique per topic ignoring case; deleting one deletes its scores. |
| threads | The discussion read for a result item: address, source used, title, post, first comments, content hash, attempts and error. |
| thread_scores | Score and passage of a discussion against one subtopic, keyed by item, subtopic, embedding namespace and discussion content hash. |
| subtopic_findings | First subtopic match of a discussion within one topic: item, topic, run, time found and time marked reviewed. |
| generations | Draft replies generated by earlier versions: item, topic project and label, winning subtopic text, agent, model, effort, status, comment, error, log file name and times. Read-only; nothing inserts or changes rows. |

The schema version is 6. The subtopic, discussion and generation tables are created on open with `CREATE TABLE IF NOT EXISTS`, so an existing version-6 database gains them without a migration. A new or empty database receives this schema. A database written with another schema version is rejected with `DB_VERSION`, naming the file to remove; Scout performs no data migration and keeps no compatibility path for earlier schemas. Foreign keys, WAL and a five-second busy timeout protect persistence. Network calls and inference run outside write transactions. Each tool call, each cycle task and the daemon open their own SQLite connection; WAL and the busy timeout serialize their writes, and every write transaction completes synchronously, so a tool's write never interleaves inside a cycle's transaction.

### Identity and refresh

Topic keys use Unicode NFKC normalization, collapsed whitespace and lowercase. Adding an existing key must be idempotent; removing it only deactivates it. Restoring it must retain search history and findings.

Items contain platform, kind, external ID, title, text, URL, author, publication date, discussion/parent IDs and raw JSON. Identity hashes platform, kind and external ID; the URL is the fallback ID. Canonical URLs discard common tracking parameters while preserving comment parameters and fragments. Invalid dates become null and freshness uses first collection time. Content updates retain that first collection time.

A successful poll must commit content and polling state together. A malformed feed must leave previous content and validators intact. Attempt timestamps are independent of success so failed calls also respect cooldowns. Persisted errors must remain visible until a successful retry. Each run recomputes every active topic's feed set from its terms, tags and the enabled sites, enables those feeds and disables the topic's other feeds while retaining their records. A source keeps the identifier of the site that produced it; deleting a site leaves its sources and entries stored.

### Feed provenance

Ranking and the interface must require a matching source, item and current content hash in `feed_source_items`, linked to an RSS or RSSHub source of that topic. Feed provenance commits with content and validators. New feed validators and skipped outcomes are saved after successful inspection. An unknown tag records an explicit skip; malformed feeds and network failures remain errors.

### Runs, results and failure

The application must evaluate content using the current intent hash, content hash and [embedding namespace](../wiki.html#definition-namespace). Sources shared by active topics must be polled once per interval. Feed failures must preserve successful collection, keep the run's other results and mark the run `partial`. An inference failure marks the run `failed` and records no findings for it. Stopping monitoring or cancelling the cycle task marks the run `aborted`; a task that ends during a run leaves it `running` until the daemon marks it `interrupted`, when it sees the task end or when it starts. Data committed before an abort or crash remains valid.

A run's passing set deduplicates canonical URLs across topics, retains the highest score and lists all matching topics. It has no size limit. After ranking, every passing URL without a `findings` row receives one that names the run; existing rows never change, so a URL is new exactly once. A finding is new until `seen_at` is set by the operator opening it or marking it reviewed. Subtopic matches follow the same rule in `subtopic_findings`, keyed by item and topic: after scoring, every discussion and matched topic pair that currently has a subtopic of that topic at or above the threshold receives a row naming the run if it has none, and the row stays new until the operator marks it reviewed; opening the discussion does not set `seen_at`. Changed content can be reevaluated and remains visible, but it is not marked new again, including after topic removal and restoration. Storage has no automatic retention or pruning policy.

### Monitoring state and concurrent access

Monitoring must be controlled only through the `settings` rows. `scout_monitor_start` validates the interval, refuses while monitoring is on (`MONITOR_RUNNING`) or while a run or cycle task is still recorded (`MONITOR_STOPPING`), and in one transaction saves the interval, clears `monitor:lastStartedAt` and sets `monitor:running`. `scout_monitor_stop` clears `monitor:running`. A cycle is due when monitoring is on and either no start is recorded or the interval has passed since `monitor:lastStartedAt`; a saved interval that is no longer offered counts as hourly. The [agent daemon](../wiki.html#definition-agent-daemon) is the only writer of `monitor:taskId`, `monitor:lastStartedAt` after a start, `monitor:lastTaskId` and `monitor:daemon`. Status reads derive `cycleRunning`, `currentRun`, `lastRunId` and `nextRunAt` from these rows and the `runs` table, so every process sees the same state. The [agent runtime specification](DS009-agent-runtime.md) defines the daemon's protocol.

### Generated comments

The `generations` table remains part of schema 6 so existing databases open without migration. `discussionsView` attaches to each discussion only the rows of its topic with status `done` and a comment, oldest first, exposing id, comment, agent, model, subtopic and finish time. No code path inserts, updates or deletes generation rows, and log files they name are not read.
