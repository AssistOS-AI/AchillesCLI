Overview / Operator guide

Operator guide

Open the promotionScout agent, describe a topic, check the sites it watches and turn on monitoring to receive new public discussions with relevance scores and original passages in your browser.

Open the agent

Enable the agent in a Ploinky workspace that has the AchillesCLI repository installed; its agent id is agent:AchillesCLI/promotionScout. Ploinky starts it in the assistos/ploinky-node container image, which supplies Node.js 24, Git, Python, make and a C++ compiler for the RSSHub build. Then open /promotionScout/ on the Ploinky router address while signed in. The router accepts only authenticated users and redirects the agent root to the web interface at /promotionScout/web/.

Before every start, the agent's install step prepares its data directory. The first start writes the configuration and SQLite database, downloads the default embedding model (about 309 MB) and fetches and builds a pinned RSSHub source, which takes several minutes; Ploinky allows up to an hour for the agent to become ready. Ploinky itself installs the npm dependencies declared in package.json; the install step only checks that they are present and stops with SETUP_REQUIRED, naming the missing packages, otherwise.

If the agent fails to start, read runtime/install.log in its data directory (.data/promotionScout/runtime/install.log in the workspace): Ploinky removes the failed container together with its log, but the install step keeps its own output and exit status there.

Later starts reuse every completed stage, so they take seconds. A stage that failed, for example because the network was unavailable during the model download, is retried at the next start while the successful stages are kept. Starting the agent does not read any feed.

Once installed, the agent runs two processes: the bundled Ploinky AgentServer, which answers the MCP tools the web interface calls and serves its files, and the agent daemon, which keeps RSSHub running and starts monitoring cycles. The Monitor tab shows whether the daemon responds.

All data lives in the agent's data directory, .data/promotionScout in the Ploinky workspace, mounted at /data inside the container. The agent's code directory is read-only.

Tools behind the interface

Every action in the web interface is one MCP tool call through the router at /promotionScout/mcp, made with your router session. Authenticated users of the workspace can call the same tools from other MCP clients; the web interface specification lists them. The scout_run_cycle tool that runs a monitoring cycle is internal: only the agent itself can call it.

Topics, sites, monitoring and results are managed in the web interface. Only one agent instance can use a data directory at a time.

Describe topics

Open the Topics tab and type a topic of a few words. The other two fields are optional: leave them empty and Scout derives them, showing the derived values in grey while you type.

FieldPurposeExample
TopicThe interest in a few words or a sentence. The model compares every collected entry with it.AI gaming news
Search termsUp to five short phrases, comma separated, sent to search sites. Empty: derived from the topic.derived: ai gaming
TagsUp to five subjects, comma separated, sent to tag sites. Empty: derived from the topic.derived: ai gaming, ai, gaming

Derived values are marked auto in the topic table. Derivation works best for topics of two to four words; for a long sentence, or for a concept such as steam deck that should not be split, type the terms and tags yourself. Short search terms find more posts than a long sentence; a topic that names the combination, such as “AI used in video games”, keeps the ranking precise. Matching ignores capitalization and repeated whitespace, so an equivalent topic is reported as already existing. Edit opens a dialog with the topic text, search terms, tags and subtopics; empty term and tag fields show the values derived from the current text in grey, and clearing a field returns it to derivation. Changing the topic text renames it and keeps its subtopics and history; because the text is what the model compares posts with, the topic's results disappear until the next run re-ranks them with the new text. Remove deactivates a topic after a short confirmation; its history stays stored and adding it again restores it. Changes apply from the next run.

Subtopics and discussions

A topic finds posts about a subject; subtopics say which specific angle interests you. In the Topics tab, press Edit on a topic: the dialog holds its search terms, tags and subtopics. Press Add subtopic, type a subtopic such as AI-generated NPC dialogue in RPGs, change or remove existing ones, and press Save; everything is saved together. A topic can have as many subtopics as you need. The subtopic count in the topic table opens a read-only list under the topic.

For every result of a topic with subtopics, the next runs open its discussion and read the post with its first 10 comments.

Each run reads every discussion that is due, in batches of 30 that take results from each topic in turn, so a busy topic cannot keep the others waiting; matches appear in the tab after each batch, and the first run after adding subtopics can take a quarter of an hour or more when many results are waiting. Ten comments keep the text within the model's 2,048-token window in every measured case and keep the post prominent; more comments would outweigh it. A post that matched several topics in step 3 belongs to the one with the highest score, its best topic; Scout reads the discussion only when that topic has subtopics and compares the text only with them, without judging the topic again. A subtopic matches when its score reaches the subtopic threshold, 0.35, and the highest-scoring match wins.

The Subtopic matches tab lists matched discussions first: each card shows its topic, the winning subtopic, the score of every subtopic and, when expanded, the post and comments. A discussion that matches a subtopic for the first time carries a new mark and a colored edge, and the tab label counts these. Opening its link does not change the mark, so you can read a discussion and come back to it; press Mark reviewed on its card, or Mark all reviewed, when you are done. New only shows just the new ones. Switch to All read to also see discussions that matched no subtopic or could not be read, with the reason. The count line tells how many results are still waiting to be read.

Hacker News, Reddit, Lobsters, Stack Exchange, Lemmy, Mastodon, Bluesky, DEV and Discourse discussions are read through their public data, which separates comments; other pages are read as text. MetaFilter refuses page reads, so its discussions stay unread. Adding a subtopic later scores existing discussions against it at the next run. Nothing is posted and no reply is written.

Comments from earlier versions

Earlier versions of Scout could draft replies to subtopic matches. Those generated comments stay in the database: expand Post and comments on a Subtopic matches card to read them under Generated comments, after the discussion's own comments, each with the coding agent, model, subtopic and time it was written with. The agent offers no way to generate new ones.

Choose the sites

The Sites tab lists the built-in catalog: Reddit, Hacker News and Bluesky as search sites; Mastodon, DEV Community, Medium, Lobsters, Stack Overflow and Lemmy communities as tag sites; Product Hunt, Slashdot, Hugging Face daily papers, Lemmy, Ask HN, MetaFilter, Ask MetaFilter and Tildes as general feeds. For each site it shows how many feeds it currently produces, how many entries it has collected, when it was last read and whether any of its feeds fail. Disable a site to stop reading it; the choice is kept across restarts.

To add a site, give it a name, a kind and an address: a feed URL or a web page that advertises a feed, a search address containing {query}, a tag address containing {tag} with its tag style, or an RSSHub route such as /telegram/channel/name. Feeds that follow one account, such as a YouTube channel, a Substack publication or a GitHub repository's discussions, are added as feed sites. The sites and feeds page explains each option. Sites you added can be deleted; their collected entries stay stored.

Start and stop monitoring

In the Monitor tab choose how often to search, every 1, 2, 4, 6, 8 or 12 hours, once a day, every two days or once a week, and press Start monitoring. The agent daemon starts the first run within a few seconds and each next one at the chosen interval after the previous run started. The button turns into Stop and the interval locks until you stop. The tab shows the next run time, whether the agent daemon and RSSHub respond, a summary of the last run and the cycle log.

The cycle log is the live log of the current run's cycle task; after a run ends it keeps showing that run's log until the next one starts. The page refreshes it every two seconds during a run and every five seconds otherwise. If AgentServer restarted since the run, its log is no longer available; the Runs tab still holds the run's counts and errors.

Stop ends monitoring and aborts a run in progress within a few seconds, at its next request or ranked entry. Everything collected before that point stays saved. Stop does not stop RSSHub. A feed returns only its newest entries, typically 20 to 50, so with a daily or longer interval a busy site or search term can publish more posts between runs than its feed still lists, and those posts are missed. Choose hourly or a few hours for busy sources.

Monitoring is saved in the database: when the agent restarts, it resumes with the same interval until you press Stop. A run that was in progress when the agent stopped is shown as interrupted, and the next run starts at the chosen interval after it began.

Read what Scout found

Four numbered tabs follow a post through the pipeline in order: 1 Feeds lists the feeds read, 2 Collected the entries they delivered, 3 Topic matches the entries whose similarity passed the topic threshold, and 4 Subtopic matches the discussions of those matches compared with your subtopics. Each tab holds a subset of the one before it, except Feeds, which lists sources rather than posts.

The Topic matches tab lists every URL whose similarity reached the model's threshold, 0.25 for the default EmbeddingGemma, for an active topic. Each card shows the title, score, matching topics, source host, when and in which run it was first found, and the original passage that matched best. Results found for the first time carry a new mark and a colored edge, and the tab label counts them. A result stays new until you open its link, press Mark reviewed on its card or press Mark all reviewed. Only new hides the others. Each card names the site it came from, such as Bluesky or Hacker News, before the title. Below the filters, one chip per site shows how many results it has in the current selection; click a chip to see only that site, click more to combine them, or All to reset. The Sort selector orders results by new first, newest found or highest score. These choices stay in the page address, so a reload or a bookmark keeps them. A similarity score is not a probability or permission to post.

The Collected tab lists every feed entry stored for active topics before the threshold, newest first, with its score and status: passed, below threshold, not English, or not evaluated when the entry is older than seven days or has not been ranked with the current model yet. Entries collected by the latest run are marked new. The same site chips filter this list, and a Site column shows where each entry came from. Use it to judge whether the threshold suits your topics. The Feeds tab shows every concrete feed with its site, topic, last attempt, entry count and outcome. The Runs tab lists each run with its duration, status, counts and expandable error messages. Long lists are split into pages: 20 topics or sites, 25 results, 50 collected entries or feeds and 24 runs (one day) per page.

Only English posts are ranked. The topics are in English, yet about one collected post in eight was not: technical words such as RTX or Proton and tags such as #gaming are used in every language, and general feeds such as Lemmy carry every community. The model cannot reject them by itself because it is multilingual and gives a German post about AI in games a high score for its meaning. A local detector, the eld library, therefore marks other languages as not English before ranking; it runs offline, needs no model and takes a fraction of a millisecond per post. Very short titles are always kept because detectors easily misread them.

On labeled test data about three in four results were relevant. Most remaining mistakes match only part of a topic, such as an AI post for “AI in gaming”, so describe the combination explicitly, for example “News about AI technology used in video games”. Disabling general feeds you do not need also reduces noise.

Understand the scores

Every score in Scout is a similarity score: the cosine similarity between the model's vector for your text and the vector for the post. The same measure is used in both numbered steps that score: Topic matches compare the topic with an entry's title and text, and Subtopic matches compare each subtopic with the discussion's title, post and first 10 comments.

A score is not a mark out of one, a percentage or a probability, so 0.3 does not mean 30%. Scores can range from −1 to 1, but with EmbeddingGemma unrelated texts score around 0 and relevant ones usually between 0.3 and 0.65; only nearly identical texts approach 1. In the real-model check, a relevant post scored 0.63 against its topic and an unrelated one about 0, and a fitting subtopic scored 0.58 against a discussion while an unrelated subtopic scored 0.04. Differences above the threshold are useful for ordering, not as a grade.

Topics and subtopics have separate thresholds. The topic threshold, 0.25, was chosen on 95 topic/post pairs you labeled, where it kept about three relevant posts in four. The subtopic threshold, 0.35, is provisional: on 94 real discussion/subtopic pairs none was about its subtopic, yet six of them scored between 0.25 and 0.34, so 0.35 keeps them out. No relevant real discussion has been seen yet, so the value will be revisited once some appear. Discussion text is longer and mixes many comments, so a relevant discussion can still score lower than a relevant post.

What Scout does not see

Scout watches feeds, not the pages it has already found. Each run asks every due feed for its newest entries; it never revisits a topic match to look for new replies. A discussion is read once, so comments posted after that read are not seen, and a failed read is retried at most three times, a day apart. A feed lists only its newest entries, so a busy source checked rarely can publish posts that leave the feed before the next run. Scout does not open linked articles; pages built by JavaScript, such as Medium or Product Hunt, yield little more than their summary; and sites that refuse automated requests, such as MetaFilter pages, stay unread.

Refresh and request limits

Each feed is read at most once per hour, so the shortest interval is one hour. Feeds shared by several topics are read once. Requests to one host are at least a second apart, ten seconds for Reddit. A site that refuses with 403 or 429 is paused for six hours and its feeds are read after the pause; Reddit often refuses anonymous requests. Saved validators and embeddings avoid repeating unchanged work. Ranking uses a seven-day freshness window and the model's fixed threshold. A URL found by several topics appears once with all matching topics and its highest score. A URL is marked new only once, even if its text changes later.

The database schema has no migrations. If the agent reports DB_VERSION for a database written by another schema version, stop the agent and remove scout.sqlite and its -wal and -shm files from the data directory; topics then need to be added again.

Services, shutdown and errors

The agent daemon starts RSSHub when the agent starts, or reuses it when it already responds at http://127.0.0.1:1200 inside the container, and checks it every 30 seconds, starting it again if it stopped. If RSSHub cannot start, the Monitor tab shows the reason and only RSSHub feeds fail; other feeds continue. RSSHub logs live in the data directory's runtime/.

Stopping the agent stops the daemon, which stops the RSSHub process it started, and AgentServer, whose running cycle task ends. The run of that task is marked interrupted at the next start, and monitoring resumes if it was on.

Feed errors make a run partial and stay visible during their cooldown; other results of that run remain. A run whose model inference fails is marked failed and never uses substitute scores. A missing model fails the run with MODEL_UNAVAILABLE; restarting the agent lets its install step download it again.

The lifecycle lock guarantees that only one daemon or install step uses the data directory at a time, so two daemons never start the same cycles or RSSHub and the install step never replaces RSSHub or the model under a running daemon. A lock left behind by a process that was killed or by a container restart is stale: the process it names no longer exists. Scout checks the process number, its start time and the machine's boot identity, removes such a lock automatically at the next start and reports it in the agent log.
