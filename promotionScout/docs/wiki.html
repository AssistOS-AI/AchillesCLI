Overview / Wiki

Wiki

These terms describe Scout's agent runtime, web interface, saved interests, watched sites, monitoring runs, model isolation and returned results.

Web interface

The web interface is the set of static pages in the agent's web/ directory that the Ploinky router serves at /promotionScout/web/; opening /promotionScout/ redirects there. It is the place where the operator manages topics, starts and stops monitoring and reads what Scout found. Its tabs follow the order of the work: Topics, Sites and Monitor set Scout up; 1 Feeds, 2 Collected, 3 Topic matches and 4 Subtopic matches show the steps a post goes through, from the feed that delivered it to the subtopic its discussion matches; Runs keeps the history.

The page performs every action as an MCP tool call through the router with the operator's session, polls scout_status for the monitoring state and reads the live log of the current or last cycle task from the agent's task-status endpoint. The router admits only signed-in workspace users, so the page has no login of its own. It follows the system light or dark preference unless the operator chooses a theme. Closing the browser changes nothing; monitoring continues in the agent.

Topic

A topic is an interest saved in the Topics tab of the web interface. It has three parts: a description, which states the interest in a sentence and is what the model compares entries with; optional search terms for search sites; and optional tags for tag sites. The description also identifies the topic: Unicode normalization, repeated-space removal and lowercase comparison prevent duplicate interests. It can be changed in the Edit dialog; the topic keeps its subtopics and history, and the next run re-ranks its entries against the new text. Removal deactivates it while preserving associated sources, entries and result history, and hides its results; adding it again restores them. Topic changes affect the next run. A topic has no separate project folder, configuration file or schedule of its own: all active topics share one monitoring interval.

Search terms

Search terms are up to five short phrases attached to a topic, such as balcony garden or container tomatoes. Scout inserts each one into the address of every enabled search site, so each term produces one feed per site; a site that understands OR, such as Reddit, receives all terms of a topic in one combined query. Short phrases match more posts than a full sentence. When a topic has no stored search terms, Scout derives them from the topic: it keeps the significant words, drops words such as news, on or years, and forms one phrase of up to three words or several two- or three-word phrases, so AI gaming news becomes ai gaming. Derived terms are marked auto in the Topics tab. Search terms only build feed addresses; relevance is still decided by the model against the description, so a term that brings unrelated posts adds entries to the Collected tab but not to the topic matches.

Tags

Tags are up to five single subjects attached to a topic, such as gardening. Scout inserts each tag into the address of every enabled tag site after rewriting it in that site's style: joined (balconygarden), hyphenated (balcony-garden), with underscores as Lemmy community names (balcony_garden) or ASCII letters and digits only. Sites with a fixed vocabulary, such as Lobsters and Stack Overflow, know only their existing tags; an unknown tag appears as skipped in the Feeds tab. When a topic has no stored tags, Scout derives them: each two-word phrase of the topic as a compound tag, then its single significant words, at most five, so AI gaming news gives ai gaming (written aigaming on Mastodon), ai and gaming. Single-word tags bring posts about only one part of the topic, which the model then has to filter.

Subtopic

A subtopic is a free text attached to a topic that names a specific angle of it, for example AI-generated NPC dialogue in RPGs under AI gaming news. A topic can have any number of subtopics; the operator adds and removes them in the Topics tab, under the topic. Subtopics do not change which posts are collected or which become results. They decide which results Scout reads further: every result belongs to its best topic, the matching topic with the highest score, and when that topic has subtopics Scout reads the result's discussion and compares it with that topic's subtopics only, using the same local model. A subtopic matches when its score reaches the subtopic threshold, 0.35 for EmbeddingGemma, and among matching subtopics the highest score wins. Removing a subtopic removes its scores.

Discussion

A discussion is the page behind a result where people comment: a Hacker News item, a Reddit thread, a Lemmy post, a Stack Overflow question with its answers, a Bluesky post with its replies, or any other page. Scout reads it only for results whose best topic has subtopics, every due one in each run, and keeps the title, the post and the first 10 top-level comments in the order the site shows them. Sites with a public API or per-discussion feed are read through it; other pages are read as text, where comments cannot be separated and pages built by JavaScript give little more than a summary. A discussion is read once, so later comments are not seen. Reads follow the same per-host spacing and refusal pauses as feeds. The Subtopic matches tab shows each discussion with its winning subtopic and the scores of all subtopics. A discussion is new from the run in which it first matched a subtopic until the operator marks it reviewed; opening its link does not, because reading a discussion is not the same as deciding about it. Like a result, it is new only once.

Ploinky agent

A Ploinky agent is a component that a Ploinky workspace discovers from a repository directory with a manifest.json and starts in its own container. Promotion Scout is the agent promotionScout of the AchillesCLI repository, with the durable agent id agent:AchillesCLI/promotionScout and the router path /promotionScout. Its manifest selects the assistos/ploinky-node image, mounts the data directory, declares the install step and starts scripts/startAgent.sh, which runs the bundled Ploinky AgentServer and the agent daemon. The Ploinky router in front of the container authenticates users, applies tool policy and forwards requests; the agent publishes no port of its own to browsers.

MCP tool

An MCP tool is one named operation that the agent declares in mcp-config.json and AgentServer exposes through the Model Context Protocol at /promotionScout/mcp. Each call starts one short process, node tools/scout.mjs <operation>, which reads the call's input as JSON from standard input, opens the SQLite database, performs the operation and prints one JSON value. Expected problems, such as invalid input or an unknown topic, are printed as {"error": {"code", "message"}} instead of failing the call. The 21 user tools, from scout_status to scout_runs_list, carry no tags, so any signed-in workspace user may call them from the web interface or another MCP client. scout_run_cycle is tagged internal, so only an agent, in practice Scout's own daemon, may call it.

Agent daemon

The agent daemon is the long-lived Node.js process src/agent/main.mjs that scripts/startAgent.sh starts beside AgentServer. It holds the lifecycle lock, marks runs left unfinished by an earlier process as interrupted, synchronizes the built-in site catalog, keeps RSSHub running and checks it every 30 seconds, and writes a heartbeat with the service state to SQLite, which the Monitor tab shows. Every two seconds it reads the monitoring state that the tools saved; when monitoring is on and a cycle is due, it calls scout_run_cycle through the router with the Ploinky agent client and follows the resulting cycle task until it ends. It keeps no monitoring state in memory, so a restarted agent continues where the database says. When it stops, it stops the RSSHub process it started.

Cycle task

A cycle task is one run executed as an asynchronous Ploinky task of the scout_run_cycle tool. AgentServer queues it and runs node tools/run-cycle.mjs in a separate process, which loads the embedding model in a worker thread, performs the run and exits, releasing the model. Every progress line the task writes to standard error, such as Run 12: started, becomes part of the task's log, kept in full while AgentServer runs; the web interface shows it as the cycle log. The task aborts within about two seconds when the operator presses Stop, because it reads the monitoring flag, and when it is cancelled. It is stopped after 12 hours. A task does not survive an AgentServer restart: its run is then marked interrupted and its log is lost, while the run's counts and errors stay in the Runs tab.

Install step

The install step is the command sh /code/scripts/install.sh that the manifest declares and Ploinky runs in the container before every agent start. It checks that the npm packages Ploinky prepared from package.json are present, then under the lifecycle lock writes config.json if it is missing, creates the SQLite database, downloads the default embedding model when it cannot be loaded locally and fetches and builds the pinned RSSHub revision. Completed stages are recognized and skipped, so only the first start downloads and builds, which takes several minutes. A failing stage keeps the others, stops the start with SETUP_INCOMPLETE and is retried at the next start. It is the only part of the agent that downloads model or service files.

Data directory

The data directory holds everything the agent writes: scout.sqlite with its sidecars, config.json, the model files in models/, the RSSHub installation in services/ and the logs, process records and lock in runtime/. For the agent it is the workspace directory .data/promotionScout, mounted at /data in the container and named by SCOUT_DATA_DIR; the agent's code directory /code is read-only. Code run outside the agent, such as the tests, falls back to ~/.local/share/promotion-scout/, or to promotion-scout under an absolute XDG_DATA_HOME.

Generated comment

A generated comment is a draft reply to one discussion that an earlier version of Scout wrote through a coding agent when the operator asked for it. Such drafts remain in the generations table of the database. The Subtopic matches tab lists the finished ones, those with a comment, under Generated comments in a card's expandable section, after the discussion's own comments, each with the coding agent, model, subtopic and time it was written with. The agent does not create, change or post generated comments; the operator copies and posts a reply outside Scout.

Site

A site is an entry in the Sites tab that tells Scout where to read feeds. It has a name, a kind and an address template. A search site contains {query} and receives search terms; a tag site contains {tag} and receives tags; a feed site has a fixed address read once for all topics. An address is either an absolute URL or an RSSHub route beginning with /. Seventeen built-in sites come from config/sites.json; they can be disabled but not deleted. The operator can add feed URLs, pages that advertise a feed, search or tag templates and RSSHub routes, and delete them later. Each run turns the enabled sites and the active topics into concrete feeds, shown in the Feeds tab. Scout watches only these sites and does not search the rest of the web.

Monitoring

Monitoring is the state in which Scout repeats runs on a schedule. The operator turns it on with Start monitoring in the Monitor tab after choosing an interval: every 1, 2, 4, 6, 8 or 12 hours, once a day, every two days or once a week. The first run starts within a few seconds; each following run starts the chosen interval after the previous one started, or right after it when a run takes longer. Stop turns monitoring off and aborts a run in progress without stopping RSSHub. The state and the interval are saved in SQLite, so monitoring resumes after an agent restart until the operator presses Stop. The agent daemon starts each run. The one-hour minimum matches the hourly limit on reading each feed.

Run

A run is one monitoring cycle and one row in the Runs tab, executed as a cycle task. It loads the local model, builds the feeds of every active topic from the enabled sites, polls the feeds that are due, using RSSHub when one of them needs it, ranks recent entries for each active topic, records new results and reads due discussions. Its status is ok, partial when some feeds failed, failed when the model or ranking failed, aborted when the operator pressed Stop or the task was cancelled, or interrupted when its task ended without finishing it, for example because the agent restarted. The run records counts of feeds, feeds polled, skipped and failed feeds, new entries, evaluated entries, passing results and new results, together with every error message. Work committed during a run remains valid even if the run does not finish.

Watch

Watch is the internal ranking intent associated with a topic. Its hash isolates evaluations when intent or ranking semantics change. Internal SQLite tables retain the name projects for these records, but the public interface operates on topics and has no project concept.

Embedding namespace

An embedding namespace identifies compatible vectors by hashing the model profile and provider implementation version. Profiles include immutable revision, prefixes, pooling, dtype, dimensions and token limit. Query/document role and text hash further distinguish cache entries. Model or semantic changes create another namespace; old vectors remain stored. The web interface reads scores only from the current namespace, so after a model change entries appear as not evaluated until the next run ranks them.

Result

A result is a URL whose similarity to an active topic reached the threshold of the active model, 0.25 for the default EmbeddingGemma. Only verified English feed entries from the last seven days are ranked. A URL that matches several topics is one result listing every matching topic and its highest score. The Topic matches tab lists all results for active topics, not only those of the latest run. When a run finds a passing URL for the first time, Scout records that run and time; this record never changes, so the result is new exactly once. It stays new until the operator opens its link or marks it reviewed. Each result shows the original passage that matched best; it is context, not a generated reply or a guarantee that posting is appropriate.

Similarity score

A similarity score is the cosine similarity between two embeddings: the topic or subtopic text and the post or discussion. Topic matches and subtopic matches use the same measure. It is not a percentage, a grade out of one or a probability. Values can range from −1 to 1; with EmbeddingGemma unrelated texts score near 0 and relevant ones usually between 0.3 and 0.65. A post matches a topic when its score reaches the topic threshold, 0.25 for EmbeddingGemma, calibrated on labeled topic/post pairs. A discussion matches a subtopic at the subtopic threshold, 0.35, a provisional value chosen so that the irrelevant discussions seen so far stay out. Scores from different models are not comparable.

Lifecycle lock

The lifecycle lock is the file runtime/lifecycle.lock in the data directory. The agent daemon holds it while it runs and the install step holds it while it prepares files, so only one of them uses the data at a time. Tool calls and cycle tasks do not take it. It records the owner's process number, start time and boot identity. A lock whose process no longer exists, after a kill, crash or container restart, is stale and is removed automatically at the next start.

RSSHub

RSSHub is a native Node.js service, built by the install step, that turns website-specific routes into RSS feeds. Built-in sites use it for Bluesky keyword search and Hugging Face daily papers, and the operator can add other routes, such as Telegram channels, as sites. Existing RSS/Atom feeds bypass RSSHub. The agent daemon starts it at http://127.0.0.1:1200 inside the container when the agent starts, restarts it when it stops and stops it with the agent; it is not reachable through the router. If it cannot start, only its feeds fail. The service uses memory caching; Scout owns persistent SQLite storage. Some routes require credentials or a browser. RSSHub has routes only for the sites its authors support; a site with neither its own feed nor a route cannot be watched.

RSS/Atom feed

An RSS or Atom feed is an XML document listing entries with links and available metadata such as title, text, author and date. Scout reads RSS 2.0, RSS 1.0 and Atom, directly or through RSSHub; when the operator adds a web page as a site, Scout follows its same-origin feed link once. It ingests the entries without fetching their linked articles. Feed text can therefore be a summary rather than a complete article. Scout records which source supplied each entry and the hash of its current content; only entries with this feed provenance are ranked or listed in the Collected tab.

Embedding

An embedding is a numeric representation of text produced by the local model. The default EmbeddingGemma profile produces 768 normalized numbers for each topic description or feed passage. Scout uses cosine similarity to compare them. The number is model-dependent relevance, not a probability or a generated explanation. Cached embeddings live in SQLite and are isolated by model semantics, role and text.
