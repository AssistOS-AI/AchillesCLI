Overview / Architecture

Architecture

Promotion Scout runs as the promotionScout Ploinky agent. Inside one container the bundled Ploinky AgentServer answers MCP tools and serves the web interface, and the agent daemon keeps RSSHub running and starts monitoring cycles. Each cycle connects RSS/Atom collection from a catalog of sites to SQLite and CPU inference as one cycle task.

Where components run

ComponentProcess, address and lifetime
Ploinky routerThe workspace entry point outside the container. It authenticates the operator, serves the files under /promotionScout/, forwards /promotionScout/mcp tool calls and /promotionScout/task status requests to AgentServer and mediates the daemon's own call to scout_run_cycle.
AgentServerThe bundled runtime started by scripts/startAgent.sh on container port 7000. Each synchronous tool call runs node tools/scout.mjs <operation> with /code as working directory and ends when it has printed its result; scout_run_cycle runs node tools/run-cycle.mjs as a queued asynchronous task whose standard error is its live log.
Agent daemonsrc/agent/main.mjs, started beside AgentServer by the same script, which stops the container when either process exits. It holds the lifecycle lock, owns RSSHub, writes a heartbeat to SQLite and starts each due cycle through the router with the Ploinky agent client.
BrowserLoads the static pages from web/, calls the MCP tools through /MCPBrowserClient.js and reads the cycle log from the task-status endpoint; it polls scout_status every two seconds during a run and every five seconds otherwise.
RSSHubA separate native Node.js process inside the container at http://127.0.0.1:1200, started by the daemon when the agent starts, restarted when it stops and stopped when the daemon exits, unless it was started by someone else. It is not exposed through the router.
Watched sitesThird-party services such as Reddit, Hacker News (hnrss.org), Mastodon and DEV Community, reached over HTTPS for their RSS/Atom feeds.
Embedding inferenceONNX Runtime through Transformers.js in a worker thread of the cycle task process. CPU execution, no HTTP API or separate server. The model occupies memory only while a cycle runs.
SQLiteThe database file /data/scout.sqlite, opened through node:sqlite by each tool call, each cycle task and the daemon. No database server or port.

Short tool processes and the long-lived daemon share state only through SQLite in WAL mode with a five-second busy timeout. The operator's Start and Stop write the monitoring state into the settings table; the daemon reads it every two seconds, records the task of the running cycle and the time it started, and the cycle task itself reads the monitoring flag every two seconds so Stop aborts it. No HTTP server of the agent's own exists, and RSSHub binds to loopback inside the container.

Feed collection and discussion reading use the network. Model inference reads local files and performs local computation. The router owns authentication: the web interface and every user tool require a signed-in workspace user, and only the agent itself may call scout_run_cycle. The agent runtime specification defines the manifest, tools and task protocol.

One database per agent

The data directory is the agent's volume, .data/promotionScout in the Ploinky workspace, mounted at /data; SCOUT_DATA_DIR points the code at it, and outside the agent the code falls back to ~/.local/share/promotion-scout/. scout.sqlite stores active topics with their search terms and tags, sites, feeds, content, vectors, evaluations, runs, new-result marks and the monitoring state. The schema has no migrations: a database written by another schema version is rejected and must be removed. SQLite sidecars belong to that database.

Model weights and the RSSHub installation are ordinary files alongside the database. The generations table keeps the comments written by earlier versions of Scout, which the Subtopic matches tab shows read-only; nothing adds rows to it.

The daemon holds a per-directory lifecycle lock for its whole lifetime, and the install step takes the same lock before it, so a second daemon fails with a busy error. Tool calls and cycle tasks do not take the lock; SQLite transactions keep their writes consistent. Linux process identities prevent a stale PID record from stopping an unrelated process. The lock records its owner's process number, start time and boot identity; when that process no longer exists, because it was killed or the container restarted, the next start removes the lock and reports it.

On Node.js 22.22.3, node:sqlite emits an experimental-API warning. This concerns Node’s JavaScript integration and does not mean the SQLite engine itself is experimental. It is a warning on stderr, not a failed search.

Refresh and persistence

Each run builds every topic's feed addresses from its search terms, tags and the enabled sites. Feeds that a topic no longer produces stay stored but inactive. Hourly collection shares feed identity across topics. Requests to a host are spaced, a 429 is never retried, and a 403 or 429 pauses the host for six hours, recorded in SQLite. Successful polls commit records and validators together. Failed or interrupted attempts keep an error and a cooldown, preventing rapid repeated requests without disguising failure as an empty response.

Ranking uses records dated within seven days, or their first collection time if no valid date exists. Evaluation keys include content hash, intent hash and embedding namespace. Content or model changes therefore require fresh evaluation. Long text splits into passages; the highest scoring original passage becomes context. This can split sentences and lose cross-passage meaning.

Only feed entries with saved source and content-hash provenance enter ranking or appear in the interface. Unsupported sources are explicit cached skips; malformed feeds and network failures remain errors. A run takes its start time as the attempt time of every source it polls, so runs started an hour apart recheck every due source.

Runs and new results

Each monitoring cycle is a run recorded in SQLite with its counts, errors and final status. Results are combined by canonical URL across topics; Scout keeps the highest matching score and every matching topic. The threshold, 0.25 for the bundled EmbeddingGemma, is fixed per model profile and applies only to English entries. There is no result limit. The first run that finds a passing URL records it as new; the record never changes afterwards, so the same URL is never new twice. Opening a result or marking results seen clears the mark.

Source errors make a run partial and keep its other results. Inference errors mark the run failed, record no new results and never use keyword fallback. Stopping monitoring aborts the run between requests and ranked entries; work already committed stays valid. A run cut off by a killed task or an agent restart is marked interrupted when the daemon sees its task end or at the next start.

Cycles as tasks

When monitoring is on and a cycle is due, the daemon calls scout_run_cycle through the router and receives a task identifier at once. AgentServer runs the task in its own process: the task opens the database, records a run, loads the model in a worker thread, collects, ranks and reads discussions, and releases the model at the end. Each progress line it writes to standard error becomes part of the task's log, which the web interface reads from /promotionScout/task; the summary it prints is the task result. The task keeps its full log until AgentServer restarts and is stopped after 12 hours.

The daemon checks the task every two seconds. When the task completes, fails, is cancelled or is unknown to a restarted AgentServer, the daemon clears it, keeps its identifier as the last cycle task and marks any run left running as interrupted. The next cycle is due the chosen interval after the previous one started. If the task keeps running for 60 seconds after Stop, the daemon cancels it, which sends it SIGTERM and lets it record the run as aborted. A failed call, such as a router that is not ready yet, is retried after 30 seconds.

Running a cycle as a task gives it the live log and cancellation of the Ploinky task queue, and confines the model, about 1.6 GB of peak memory, to the cycle's own process. The daemon keeps no monitoring state in memory, so a restarted agent resumes monitoring from SQLite; a task never survives an AgentServer restart, which is why the daemon, and not the task queue, decides when the next cycle runs.

The model and its invocation

The bundled default is EmbeddingGemma 300M (onnx-community/embeddinggemma-300m-ONNX), a multilingual model that creates embeddings. It does not generate text. Its profile is declared in config/embedding-models.json, next to the alternative multilingual-e5-small and minilm-en profiles. EmbeddingGemma is distributed under the Gemma Terms of Use.

SelectionEnglish entries only; cosine similarity at least 0.25 (the profile threshold); every passing URL is a result, with first-time URLs marked new. Discussions of results are compared with the subtopics of the result's best topic and match at 0.35 (the provisional subtopic threshold).

Scout calls createEmbeddingService(profile, { dataDir }), then service.embed(texts, 'query') or service.embed(texts, 'document'). The adapter adds the appropriate prefix and runs the feature-extraction pipeline. Scout compares the resulting vectors with cosine(). Existing vectors and evaluations are reused when their keys match.

The install step downloads the model into models/ in the data directory and checks it with one embedding. Each run with active topics loads it in its cycle task and releases it from RAM when the run ends. Ordinary inference is offline. A missing model fails the run with MODEL_UNAVAILABLE; an inference failure fails its run. The alternative MiniLM profile is available internally, but neither the tools nor the interface select models, and Scout never falls back to it automatically.

Why this model and a worker thread

EmbeddingGemma replaced multilingual-e5-small after a comparison on 95 topic/post pairs labeled by the operator. At its old threshold e5-small showed about six irrelevant results in ten (37% precision); EmbeddingGemma at 0.25 reached 69% precision, and 74% with the English filter, at 74% recall. bge-m3 and Qwen3-Embedding-0.6B did not do better at their best thresholds. Splitting a topic into aspects that a post must all reach, and a cross-encoder reranker, made EmbeddingGemma worse, so the remaining partial matches are best reduced by topics that name the combination. The 2,048-token window fits a post with its first 10 comments; the sample is small, so only the large differences are reliable. The embeddings specification records the measurements.

Node.js runs a process's JavaScript on one thread whose event loop handles every timer, signal and request in turn. await frees that thread only while work happens elsewhere, such as network or disk; tokenization in Transformers.js and the ONNX model run occupy the calling thread, so an asynchronous call blocked the thread for 3,875 of 3,924 ms on one long post. Inference therefore runs in a node:worker_threads worker of the cycle process: the main thread sends texts with a request number and receives vectors, and the measured block fell to 1 ms. Inference takes as long as before; the cycle still notices Stop and keeps its request timeouts while the model computes.

Model replacement and cost

Profiles own immutable revision, dimensions, pooling, dtype, token prefixes, limits and the relevance threshold; thresholds differ between models and are calibrated on labeled posts. Provider implementation versions form part of vector identity. Replacing a model or its vector semantics requires a distinct namespace and fresh evaluation. The public interface uses the bundled default; maintainers extend the provider interface without coupling network connectors to an inference runtime.

A 768-dimensional float32 vector requires 3,072 payload bytes plus keys and SQLite overhead. Each passage and namespace adds entries. Ranking uses exact comparisons without an external vector database. There is no automatic cache pruning. See coding and test rules for real-model smoke checks and fixture test boundaries.
