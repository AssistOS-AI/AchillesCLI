Promotion Scout Documentation

Promotion Scout helps an operator find public discussions relevant to a project, book or idea. It runs as the promotionScout Ploinky agent of the AchillesCLI repository. The operator opens its web interface at /promotionScout/ on the Ploinky router, saves topics and starts monitoring. The agent then periodically reads the RSS/Atom feeds of a catalog of sites such as Reddit, Hacker News, Bluesky, Mastodon and DEV Community, ranks the entries with a local model and shows the relevant discussions with original passages, marking the new ones.

Embedding model: onnx-community/embeddinggemma-300m-ONNX (EmbeddingGemma, q8, 8-bit). It produces 768-dimensional vectors and accepts up to 2048 tokens per input. It runs locally on the CPU inside each monitoring cycle through Hugging Face Transformers.js and ONNX Runtime. No separate model server is required. See model execution and settings.

Running the agent

Ploinky starts the agent from promotionScout/manifest.json. Before every start, the agent's install step prepares its data directory, .data/promotionScout in the workspace: configuration, the SQLite database, the downloaded embedding model and a pinned RSSHub build. The first start therefore takes several minutes; later starts reuse everything. The agent then runs the bundled Ploinky AgentServer, which exposes its MCP tools and serves the web interface, beside the agent daemon, which keeps RSSHub running and starts monitoring cycles. Add topics with their search terms and tags in the Topics tab, review the Sites tab, choose an interval in the Monitor tab and press Start monitoring. The lifecycle specification defines installation, startup and shutdown.

From intent to review

A topic's description is the intent the model ranks against, its search terms go to search sites and its tags go to tag sites. While monitoring is on, each run builds the feed addresses for every topic, reads the feeds that are due and stores the entries in SQLite. It then scores recent entries against each topic. Entries at or above the threshold become results, and results found for the first time are marked new. Each feed is read at most hourly, and a site that refuses requests is paused for six hours. Each run executes as one cycle task, whose live log appears in the Monitor tab.

The interface shows every stage: the watched sites, the concrete feeds each topic uses, every collected entry with its score before filtering, the results after filtering and the history of runs with their errors. A failed model does not create substitute scores. The operator follows a result URL and decides whether to participate. For results of topics with subtopics, the agent reads the discussion and shows which subtopic it is about. Comments generated by earlier versions of Scout stay readable with their discussion; the agent never writes or posts replies.

Scout reads feeds directly; RSSHub participates only for routes such as Bluesky keyword search. Scout does not search the rest of the web, so discussions on sites outside the catalog are not found; the operator can add sites. SQLite also retains vectors, cached evaluations and run history.

What each component does

ComponentResponsibility
Ploinky routerAuthenticates the operator, serves the web interface files and forwards MCP tool calls and task-status requests to the agent.
AgentServerThe bundled Ploinky runtime inside the agent container. It runs one short process per MCP tool call and queues each cycle task.
Agent daemonA long-lived process beside AgentServer. It keeps RSSHub running, reads the monitoring state from SQLite and starts each due cycle as a task.
Web interfaceStatic pages in web/ that let the operator manage topics and sites, start and stop monitoring, follow the cycle log and inspect feeds, collected entries, results, subtopic matches and runs.
Site catalogBuilt-in sites from config/sites.json plus sites the operator adds; each turns search terms, tags or nothing into feed addresses.
RSSHubServes RSS for website routes, such as Bluesky keyword search and Hugging Face daily papers, on loopback inside the agent container.
RSS/Atom readerReads RSS 2.0, RSS 1.0 and Atom feeds and extracts entries with title, text, URL, author and date when available.
SQLiteKeeps topics, source state, feed entries, vectors, scores, runs, new-result marks, the monitoring state and the comments stored by robots or generated by earlier versions in one database file.
Local embedding modelTurns text into vectors inside the cycle task. Scout compares them, applies its relevance threshold and keeps the strongest original passage.

Default local model

The default is EmbeddingGemma 300M (onnx-community/embeddinggemma-300m-ONNX), using q8 weights, 768-dimensional vectors and a relevance threshold of 0.25 calibrated on labeled posts. Only English posts are ranked; a local language detector sets the others aside. Hugging Face Transformers.js loads the model through ONNX Runtime on the CPU in a worker thread of the cycle task. It has no model-server port. The install step downloads and checks it; each run loads it and releases it when the run ends, and cached vectors survive in SQLite. Model inference needs no network access after installation.

Open the documentation locally

From the promotionScout directory, run:

python3 -m http.server 8000 --bind 127.0.0.1 --directory docs

Open http://127.0.0.1:8000/. Stop the documentation server with Ctrl+C. This serves only documentation and does not start the agent or RSSHub. The Repository menu links need the whole AchillesCLI directory served instead. Diagram rendering loads Mermaid from its CDN; the surrounding text and tables remain available without that library.

Development and product scope

The product distributes a Ploinky agent with MCP tools and a static web interface, not a runtime skill catalog. Source modules are separated into application workflows, the agent runtime, tool entry points, the browser interface, network providers and embeddings. Built-in Node tests cover feed selection, collection, persistence, the MCP operations, the daemon and cycle tasks with local fixtures; a real-model smoke check covers offline inference. Imported development instructions keep their examples inside their own folders. Coding style and test organization are defined in DS001.
