Sessions and Asynchronous Tasks

A conversation session preserves your work with AchillesCLI. A delegated task sends a bounded piece of work to another agent and lets it run independently while your current conversation remains available.

Multiple sessions in one folder

AchillesCLI can keep multiple durable conversation sessions for the same selected project folder. Each session has its own transcript and model context, but all sessions operate against the same workspace and therefore see the current state of its files. Creating a session does not copy the project, and resuming an older session does not roll files back.

CommandEffect
/sessionOpens or refreshes the session picker, including the option to create a session and the saved sessions for this workspace.
/session newCreates a new conversation history in the current folder and selects it.
/session resume <session-id>Loads a saved conversation and makes it the active session.
 
/session new
/session
/session resume <session-id-from-the-picker>

Session data is stored under the selected workspace's .achilles-cli/sessions/ directory. The active session selection is also workspace-local, so moving to another folder gives you that folder's own session list and current selection.

Delegate work asynchronously

Through Ploinky, AchillesCLI can delegate coding work to Codex, OpenCode, or PI. A launcher submits the request to the named agent and creates a persistent local background task. Submission does not block the main AchillesCLI conversation: you can keep asking questions, work on another part of the project, or start another delegated task while the agent runs.

You can request a named agent in natural language through Ploinky WebChat, for example:

Ask Codex to add tests for the parser.
Use OpenCode to refactor the configuration loader.
Have PI investigate the failing integration test.

AchillesCLI selects the matching launcher for explicit Codex, OpenCode, or PI task requests. Each agent keeps its own execution context; the model selected for the main AchillesCLI conversation is not silently imposed on the delegated agent.

Inspect and control tasks

AchillesCLI gives every delegated execution a stable local task identifier. The workspace journal retains the target agent, remote task reference, status, and logs needed for later inspection and supported controls.

CommandEffect
/tasks [count|all]Lists recent or all stored task summaries for the current workspace.
/task view <task-id>Shows the stored task metadata and latest log content.
/task continue <task-id> <prompt>Sends a follow-up prompt through the task's stored continuation capability and keeps the same local task identifier.
/task stop <task-id>Requests cancellation of a queued or running task.
 
/tasks
/task view task-7
/task continue task-7 add regression tests for the edge case
/task stop task-7

Continue a delegated task

Continuation is useful when the first result needs another iteration. Instead of restating the original assignment in a new task, send a follow-up prompt to the existing task. AchillesCLI resolves the delegated agent and its opaque continuation handle from workspace-owned storage, appends the prompt to the task timeline, and preserves the same local task identifier.

Only a task with a compatible stored continuation capability can be continued. If a provider or completed task does not expose that capability, AchillesCLI reports that boundary instead of inventing a new unrelated execution.

WebChat workflow

Ploinky WebChat uses the same session and task contracts as the terminal CLI, but presents their structured state through interface controls. Session lists make it easier to create or select a conversation without typing its opaque identifier. Task entries expose current status, logs, and supported controls, so viewing, continuing, or stopping work is more convenient than entering each slash command manually.

Actions initiated by these controls still pass through AchillesCLI's session and task managers. Switching interfaces does not create a second source of truth: CLI and WebChat observe the same workspace-local records.

Standalone and Ploinky boundaries

Conversation sessions are a core AchillesCLI feature and are available when the CLI runs independently. Delegation to Codex, OpenCode, and PI depends on Ploinky because Ploinky supplies the managed target agents, lifecycle activation, routing, and authorization used by the launchers. A standalone AchillesCLI process without those Ploinky services can continue local conversations and use local skills, but it cannot provide the managed cross-agent delegation workflow described on this page.

For the exact slash syntax, including task model and provider-login controls, see the Usage command reference. For skill availability controls, see Skills.
