AchillesCLI Documentation

AchillesCLI is a skill-oriented CLI runtime built on AchillesAgentLib. This documentation tracks the implemented runtime and keeps detailed specifications synchronized with the codebase.

Architecture Scope

Runtime package: achilles-cli/ (entrypoint, REPL, UI, schemas, skills)
Tests: tests/ and achilles-cli/tests/
Specifications: docs/specs/DS000-DS012

Ecosystem Integration

AchillesCLI integration boundaries are specified against: Ploinky, AchillesAgentLib, and AchillesIDE in DS010.

Interruption Model

AchillesCLI supports ESC cancellation for long-running prompt and slash-command executions. Cancellation is propagated as an abort signal to runtime calls, interrupted turns are not persisted to command history, and the next user input resumes normal interactive flow. In webchat runtime mode (non-TTY stdin), ESC is accepted as a standalone input line to abort the current prompt.

Orchestrated Response Policy

AchillesCLI asks for user-facing responses that are short and to the point, but it does not prefer one-word answers. This presentation guidance does not replace the structured planner contract owned by AchillesAgentLib; natural-language turns still require a valid planner decision before any text is returned through the reserved final-answer tool.

WebChat Progress

In webchat runtime mode, AchillesCLI emits structured progress metadata before loop-session tool calls. The metadata carries the planner reason for the selected tool and is intended for browser UI progress rendering, not for transcript or final-answer text. The startup intro is skipped when PLOINKY_WEBCHAT_HAS_HISTORY=1 and otherwise runs normally; no WebChat session-id environment variable is required by AchillesCLI. Asynchronous AgentServer tools are detached from the active WebChat reply: AchillesCLI acknowledges the start with the generic text Task started., while the task module shows the target runtime id and description, follows the remote task through the router, and emits dedicated lifecycle and log envelopes. Ongoing tasks are reattached from the workspace task journal if the WebChat runtime is recreated. Resumable coding tasks forward a generic opaque continuation handle after completion. The provider session stays private to its agent; WebChat starts later turns as new remote executions while keeping one stable local task id. Runtime errors include the first recognized AchillesCLI, AchillesAgentLib, or Ploinky source frame as a Markdown link through the authenticated workspace-file route. The underlying AchillesAgentLib message is preserved so missing model text, invalid planner output, provider status failures, and execution limits remain distinguishable. Unknown absolute stack paths and serialized provider response bodies remain hidden.

Repository Maintenance

Cloned skill repositories live under .achilles-cli/repos/. The slash command /update repos runs git pull in each cloned repository and reports aggregated per-repository failures with a failed to update repos: message.

Task Inspection

The deterministic /tasks [count|all] command is available in both the terminal REPL and WebChat. It reads the current workspace task journal without changing task state. By default it lists the ten most recently updated tasks with their status, description preview, target agent, and update time. Terminal task states may include the final five log lines, bounded to 2 KiB per task; ongoing logs remain on the existing WebChat lifecycle surface. Terminal use inspects persisted workspace tasks but does not detach new launcher calls.

MCP Tool Exposure

AchillesCLI exposes its skill catalog as MCP tools via the AgentServer mechanism. Each user skill is exposed as execute_<sanitised_skill_name> with an input schema. WebChat clients query this catalog at session start to populate slash-command autocomplete menus. For AchillesCLI slash commands, WebChat calls the dedicated command-catalog MCP tool (list_achilles_cli_commands) and receives a structured command+subcommand catalog. The tool accepts the WebChat working dir and uses AchillesAgentLib discovery to add available skill names as argument completions for slash commands that operate on skills. If a skill descriptor contains ## Help, that text is returned as the completion description so remote UIs can show invocation guidance beside the skill name. If no tools are available, clients silently fall back to an empty command list.

Workspace Model Selection

/model <model-name> selects an exact model or cascade from the authenticated local Soul Gateway catalog and stores it in .achilles-cli/settings.json for the current workspace. WebChat keeps the full catalog searchable inside a fixed-height, progressively rendered suggestion list; typing part of a model, provider, tag, or description narrows the list. The terminal uses an interactive search selector. The WebChat runtime publishes that explicit settings value through generic runtime-state metadata, allowing the browser to show it beside the agent name without storing model data in chat history. This badge is the configured model, not the effective Soul Gateway leaf used for an individual response. Running /tier removes the explicit saved model selection and clears the badge.

Semantic Copilot Routing

AchillesCLI Copilot owns semantic provider routing. Ploinky WebChat supplies only the generic envelope, sanitized references, and selected-agent invocation token. Non-slash Copilot turns route through copilot-router, which may call deterministic launcher cskills such as launch-open-interpreter, launch-web-search, or launch-opencode. Explicit opencode or opencodeAgent requests route to launch-opencode before generic execution launchers. Deprecated provider tokens such as @open-interpreter remain ordinary chat text. Explorer launch metadata may add generic parameters such as forward-envelope=1 and workspace-dir, but provider tags, relay tool names, and provider agent ids stay out of WebChat launch URLs.

OpenCode Agent Provider

The opencodeAgent Ploinky agent exposes OpenAI-compatible /v1/chat/completions and /v1/models handlers through AgentServer. Chat completions execute OpenCode in the Ploinky-provided WORKSPACE_PATH, and model discovery returns the OpenCode provider/model catalog for Soul Gateway. AchillesCLI does not include OpenCode, PI, Codex, GPTResearcher, or Search Agent in its manifest dependency graph, and those workers declare startup: manual. Their launchers check Marketplace runtime state, enable an installed target in explicit global mode only when needed, wait for readiness, and then invoke MCP; GPTResearcher starts Search Agent first. The OpenCode and PI launchers accept only the plain task text and leave model selection entirely to their target agents. PI runs in print mode with a persisted session id and directory. OpenCode tasks use the provider's default formatted output and resolve the created session through a separate random-title lookup before using --session when resumed. Both wrappers relay provider stdout and stderr unchanged into live task logs, without parsing or synthetic tool-status messages. Both agents keep provider session details in private persistent storage behind an opaque UUID handle, expose a policy-checked continue-task tool, and request full log retention. Their structured wrapper result exposes only answer text to ordinary MCP callers while preserving continuation metadata on the asynchronous task. This contract is specified in DS012.
