AchillesCLI Documentation

AchillesCLI is a skill-oriented CLI runtime built on AchillesAgentLib. This documentation tracks the implemented runtime and keeps detailed specifications synchronized with the codebase.

Architecture Scope

Runtime package: achilles-cli/ (broker, sandboxed entrypoint, REPL, UI, schemas, skills)
Tests: tests/ and achilles-cli/tests/
Specifications: docs/specs/DS000-DS013

Workspace Sandbox and Bash Permissions

src/cli.mjs stays outside Bubblewrap as the trusted broker and starts src/index.mjs, MainAgent, and skill execution inside a filesystem sandbox scoped to the selected workspace. Runtime code and dependencies are read-only, temporary storage is isolated, and network access remains shared. The Bash skill only parses commands and delegates execution; it contains no permission prompts or risk policy. /permissions ask-for-approval requires an explicit allow, deny, or always allow. /permissions full-access runs Bash automatically only inside the current workspace. Approvals never widen the filesystem sandbox, and there is no outside retry in the current implementation. The selected mode is stored per workspace under the permissions key in .achilles-cli/settings.json and restored at startup. Missing or invalid values fall back to ask-for-approval. The same settings object keeps the selected model and conversation currentSessionId. It is unversioned and contains no version key; reusable exact-command approvals remain session-local. In WebChat, that decision appears in a dedicated three-choice selector while the original tool call remains suspended; it is control traffic and is not stored as a user or assistant message. The Broker authorizes Bash but never executes it. The local executor runs inside MainAgent's existing Bubblewrap namespace and starts each command directly as a child process, without creating another Bubblewrap sandbox. It captures stdout and stderr without writing them to the AchillesCLI process streams. Bash returns the ordinary command output or execution error only to the agentic session, and the user sees the agent's final answer. A denial skips the Bash handler and becomes a normal planner result containing the exact tool name, exact parameters, and denial reason, allowing the same turn to finish without exposing approval protocol data. Reusable approvals are session-local and bound to the exact tool name and params. Bubblewrap uses a private /proc when the runtime permits it; nested unprivileged WebChat containers use an empty /proc fallback rather than exposing the outer container's process filesystem.

Ecosystem Integration

AchillesCLI integration boundaries are specified against: Ploinky, AchillesAgentLib, and AchillesIDE in DS010.

Interruption Model

AchillesCLI supports ESC cancellation for long-running prompt and slash-command executions. Cancellation is propagated as an abort signal to runtime calls, interrupted turns are not persisted to command history, and the next user input resumes normal interactive flow. In webchat runtime mode (non-TTY stdin), ESC is accepted as a standalone input line to abort the current prompt.

Orchestrated Response Policy

AchillesCLI asks for user-facing responses that are short and to the point, but it does not prefer one-word answers. This presentation guidance does not replace the structured planner contract owned by AchillesAgentLib; natural-language turns still require a valid planner decision before any text is returned through the reserved final-answer tool.

WebChat Progress

In webchat runtime mode, AchillesCLI emits structured progress metadata before loop-session tool calls. The metadata carries the planner reason for the selected tool and is intended for browser UI progress rendering, not for transcript or final-answer text. AchillesCLI loads its current workspace conversation at startup and skips the intro when that session has history. The prior natural-language turns are supplied once as initialHistory on the first normal prompt; slash commands do not consume that pending hydration. Commands visibly submitted in WebChat are retained as presentation-only session records and excluded from model context, while silent UI control commands are not stored. AchillesCLI publishes __webchatSession current, list, and selected snapshots so Ploinky can render session UI without owning persistence. Runtime-state metadata carries the selected model only and has no process-instance identifier. WebChat prompts use a recoverable serial queue. Errors from post-turn workspace-skill refresh are logged without rejecting later messages, and a refresh that remains pending for five seconds stops gating the next prompt. AchillesCLI also publishes a hidden workspace-file snapshot at startup and added/removed deltas after periodic five-second scans. It refreshes the index immediately before emitting a response so files created by the current turn are visible to WebChat without waiting for the timer. Ploinky can use this volatile index to link only paths that currently exist while the authenticated workspace-file route remains responsible for every actual read. Asynchronous AgentServer tools are detached from the active reply in single-shot, terminal, and WebChat modes: AchillesCLI acknowledges the start with the generic text Task started., while the task module shows the target runtime id and description, follows the remote task through the router, and persists lifecycle metadata and logs under .achilles-cli/tasks/. Ongoing tasks are reattached whenever an AchillesCLI process is recreated; WebChat mode additionally emits dedicated lifecycle and log envelopes. Resumable coding tasks forward a generic opaque continuation handle after completion. The provider session stays private to its agent; AchillesCLI starts later turns as new remote executions while keeping one stable local task id. Runtime errors include the first recognized AchillesCLI, AchillesAgentLib, or Ploinky source frame as a Markdown link through the authenticated workspace-file route. The underlying AchillesAgentLib message is preserved so missing model text, invalid planner output, provider status failures, and execution limits remain distinguishable. Unknown absolute stack paths and serialized provider response bodies remain hidden.

Conversation Sessions

Durable conversations live under .achilles-cli/sessions/. The selected currentSessionId is stored in .achilles-cli/settings.json beside model and permissions. Terminal users can open the selector with /session, create a conversation with /session new, and resume one with /session resume <session-id>. WebChat autocomplete shows saved conversation names after /session resume while inserting the corresponding session id, and its Sessions control refreshes the same list through /session. Visible WebChat slash commands and their responses are restored after refresh without entering model history. When such a command starts asynchronous work, each task reference is stored in the same ordered session so its task item is restored together with the command; UI-originated session and task-control commands remain silent.

Repository Maintenance

Cloned skill repositories live under .achilles-cli/repos/. The slash command /update repos runs git pull in each cloned repository and reports aggregated per-repository failures with a failed to update repos: message.

Task Inspection

The deterministic /tasks [count|all] command is available in both the terminal REPL and WebChat. It reads the AchillesCLI-owned workspace task journal without changing task state. By default it lists the ten most recently updated tasks with their status, description preview, target agent, and update time. Terminal task states may include the final five log lines, bounded to 2 KiB per task; ongoing logs remain on the existing WebChat lifecycle surface. /task view <task-id> reads the complete stored log, /task stop <task-id> cancels the stored remote execution, and /task continue <task-id> <prompt> resumes a compatible terminal task without changing its local id. Terminal autocomplete shows task names and inserts ids after the selected action. WebChat uses these same commands for its Tasks overlay and task page; it does not own task persistence or actions. UI-originated task commands do not add acknowledgements or errors to the main chat. On continuation, AchillesCLI appends the submitted prompt to the durable task log first with a visible you> prefix, publishes that delta, and then appends provider output in arrival order.

MCP Tool Exposure

AchillesCLI exposes its skill catalog as MCP tools via the AgentServer mechanism. Each user skill is exposed as execute_<sanitised_skill_name> with an input schema. WebChat clients query this catalog at session start to populate slash-command autocomplete menus. For AchillesCLI slash commands, WebChat calls the dedicated command-catalog MCP tool (list_achilles_cli_commands) and receives a structured command+subcommand catalog. The tool accepts the WebChat working dir and uses AchillesAgentLib discovery to add available skill names as argument completions for slash commands that operate on skills. If a skill descriptor contains ## Help, that text is returned as the completion description so remote UIs can show invocation guidance beside the skill name. The same catalog advertises ask-for-approval and full-access as the two argument choices for /permissions, allowing WebChat to render the supported modes directly. If no tools are available, clients silently fall back to an empty command list.

Workspace Model Selection

/model <model-name> selects an exact model or cascade from the authenticated local Soul Gateway catalog and stores it in .achilles-cli/settings.json for the current workspace. WebChat keeps the full catalog searchable inside a fixed-height, progressively rendered suggestion list; typing part of a model, provider, tag, or description narrows the list. The terminal uses an interactive search selector. The WebChat runtime publishes that explicit settings value through generic runtime-state metadata, allowing the browser to show it beside the agent name without storing model data in chat history. This badge is the configured model, not the effective Soul Gateway leaf used for an individual response. AchillesCLI decorates AchillesAgentLib's standard invoker with the explicit soul_gateway provider key and forwards the selected model identifier unchanged. The local model catalog supports selection and metadata but is not an execution allowlist; Soul Gateway validates and routes the current identifier, including agent-backed models introduced after the AchillesCLI process started. Running /tier removes the explicit saved model selection and clears the badge.

Semantic Copilot Routing

AchillesCLI Copilot owns semantic provider routing. Ploinky WebChat supplies only the generic envelope, sanitized references, and selected-agent invocation token. Non-slash Copilot turns route through copilot-router, which may call deterministic launcher cskills such as launch-open-interpreter, launch-web-search, or launch-opencode, or launch-codex. Explicit opencode or opencodeAgent requests route to launch-opencode before generic execution launchers; explicit codex or codexAgent requests similarly route to launch-codex. Deprecated provider tokens such as @open-interpreter remain ordinary chat text. Explorer launch metadata may add generic parameters such as forward-envelope=1 and workspace-dir, but provider tags, relay tool names, and provider agent ids stay out of WebChat launch URLs.

Coding Agent Providers

The opencodeAgent Ploinky agent exposes OpenAI-compatible /v1/chat/completions and /v1/models handlers through AgentServer. Chat completions execute OpenCode in the Ploinky-provided WORKSPACE_PATH, and model discovery returns the OpenCode provider/model catalog for Soul Gateway. Every published model uses the single functional umbrella tag coding-agent; tool support, vision, limits, and pricing remain structured model metadata. AchillesCLI does not include OpenCode, PI, Codex, GPTResearcher, or Search Agent in its manifest dependency graph, and those workers declare startup: manual. Their launchers check Marketplace runtime state, enable an installed target in explicit global mode only when needed, wait for readiness, and then invoke MCP; GPTResearcher starts Search Agent first. The OpenCode, PI, and Codex launchers accept only the plain task text and leave model selection entirely to their target agents. PI tasks run in JSON event-stream mode with a persisted session id and directory. The wrapper parses that stream incrementally and forwards only readable assistant text and de-duplicated textual tool output into the live task log. Lifecycle events, thinking metadata, signatures, encrypted content, and usage data stay out of the visible stream; the final assistant message supplies the task result. Its interactive CLI, initial task runner, and continuation runner share PI's persistent default configuration directory under the agent home, so OAuth logins and provider settings apply consistently. PI and Codex install their packages and stable launchers under $HOME/.local, allowing the same profiles to run in containers and Linux host sandboxes without writing to read-only system paths. Their installers invoke npm through an absolute CLI path selected for the container or mounted Bubblewrap Node runtime. Ploinky maps that home to the enabled instance's persistent data directory, so CLI installation and provider state survive runtime recreation. Codex initial and continuation tasks run with workspace-write confinement rooted at the selected project directory and an approval policy of never. This keeps ordinary workspace edits non-interactive while filesystem operations outside the permitted roots fail instead of disabling the Codex sandbox. OpenCode tasks use the provider's default formatted output and resolve the created session through a separate random-title lookup before using --session when resumed. OpenCode relays provider stdout and stderr unchanged into live task logs without synthetic tool-status messages. Before AgentServer starts, the agent's profile installer installs the current OpenCode release and atomically writes the repository-owned $HOME/.config/opencode/opencode.json. That config adds the OpenAI-compatible soul-gateway provider and its fast, deep, and plan models using Ploinky-injected router and agent-identity environment values; it stores no credential, selects no default model, and leaves other providers available. OpenCode's exported session data is inspected only off-stream to identify the last assistant answer for final-result metadata, allowing WebChat to show intermediate output in grey while keeping the raw visible stream unchanged. OpenCode, PI, and Codex keep provider session details in private persistent storage behind an opaque UUID handle, expose an internal policy-checked continue-task tool for verified AchillesCLI calls, and request full log retention. WebChat sends the CLI command and never invokes the provider tool directly. Their structured wrapper result exposes only answer text to ordinary MCP callers while preserving continuation metadata on the asynchronous task. Before resuming, each provider resolves its current model internally: OpenCode reads its persistent recent-model state, while PI merges persistent global defaults with project-local settings and also preserves the effective thinking level. The wrappers pass those choices explicitly alongside the stored session identity; unavailable state falls back to native resume selection. Codex parses its JSONL stream incrementally and forwards agent and completed command text without wrapper prefixes while preserving stderr byte-for-byte. Its continuation stores only the thread id and original project directory and invokes codex exec resume without a model override, so the currently configured model is used for the new turn. These contracts are specified in DS012 and DS013.
