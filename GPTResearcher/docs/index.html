GPTResearcher Agent Documentation

GPTResearcher is a manual-start Ploinky worker that turns a research question into a Markdown report. It uses Soul Gateway for language and embedding models, SearchAgent for web results, and optional files from the selected workspace as local research material.

What it does

The agent runs the GPT Researcher pipeline, lets that pipeline form its own subqueries, collects web and optional local context, writes the report, and returns the report path together with available sources, cost data, collected context, and a bounded log tail. The report is saved in the request's working directory with a timestamped filename.

Start research from AchillesCLI

GPTResearcher is designed primarily for agent-to-agent use. In AchillesCLI, request it by name through Ploinky WebChat or run its launcher skill explicitly:

Ask GPTResearcher to compare the supported authentication flows.
/exec launch-gpt-researcher Compare the supported authentication flows.

The launcher starts SearchAgent and GPTResearcher when necessary, submits the research asynchronously, and returns control to AchillesCLI. Use /tasks and /task view <task-id> to follow the result.

Research input

FieldMeaning
queryThe required research question used for web research.
contextOptional instructions or supporting data passed separately from the main query.
reportTypeThe GPT Researcher output type. The default is research_report; supported launcher values also include resource, outline, custom, subtopic, and deep reports.
workingDirA directory confined to WORKSPACE_PATH. AchillesCLI supplies its active working directory and callers cannot redirect the launcher to another workspace.
useLocalDocsDefaults to true. Existing local files select hybrid research; false or an empty directory selects web-only research.

Research flow

Settings and persistence

The nonzero container user installs its Python environment and upstream application below $HOME/gpt-researcher. Installation, UI startup, and the MCP launcher use the same agent-owned paths; the shared runner code in /opt stays read-only.

These launchers disable Python bytecode writes before Python starts, including automatic startup imports and child processes. Readiness applies the same policy. Importing adapters or the UI leaves the integration source and selected upstream checkout unchanged, without removing or ignoring generated files.

The UI and MCP research tool use the same upstream checkout. Installation builds the Python package from that checkout after installing its requirements, replacing any separately installed PyPI copy. Native gates verify the real import and record the selected source revision.

The agent persists non-secret choices for its fast, smart, and strategic language models, embedding model, and SearchAgent provider in its Ploinky home. The GPTResearcher settings panel reads model choices from Soul Gateway and lets the user update these values. Provider keys remain owned by SearchAgent or the configured model provider and are not written into the GPTResearcher settings file.

Boundaries

Generated-local model access fails with PLOINKY_LOCAL_GENERATED_CONSUMER_NOT_CERTIFIED before the Soul Gateway adapter reads routing credentials. The worker must not treat a Box descriptor or an image installation check as proof of successful research. An authorized research request can complete only when its model and search transport satisfy their admission contracts.

The manifest pins the Bubblewrap runner image by digest. It provides Node 24 and Python 3.12 on Debian Trixie, with native amd64 and arm64 checks for Git transport, sandbox confinement, and a cold GPTResearcher installation.

The selected index sha256:9b6c08cf78fd0a29acfbe2e45ea2ee26efe6fde49c7f3db8b3aadfa30f2d53f8 passed both architecture gates in native build 33662621018, including package/source consistency and UI readiness with networking disabled.

The research working directory must remain inside WORKSPACE_PATH. GPTResearcher does not call external search providers directly; every web query goes through SearchAgent. Local filenames are not concatenated into the web query, and local documents are exposed only when hybrid research is active. The worker is optional and starts only for a research request.
